# Framework Overview

Every count of AI incidents rests on a definition, and the definitions differ: the [OECD](/rival-ai-incident-definitions/definitions/oecd/) counts an event that "directly or indirectly leads to" harm, [CSET](/rival-ai-incident-definitions/definitions/cset/) requires harm that "can be directly linked to" an AI's behavior, and the [AI Incident Database](/rival-ai-incident-definitions/definitions/aiid/) admits "an alleged harm or near harm event", so the same incidents give different counts depending on which definition is applied, and a reported number rarely says which one it used.

This framework makes that dependence measurable: it writes each published definition as a rule on coded data, applies every defensible reading of each rule to the same incidents, and reports which incidents each rule counts, where the rules part, and which results hold under every reading, without ranking the definitions or naming one as correct. The [home page](/rival-ai-incident-definitions/) walks through one case.

The [Study Overview](/rival-ai-incident-definitions/study/) describes how this framework is used for a preregistered study analyzing the disagreement between rival definitions.

## Pipeline

| Step | Question | What comes out | Fixed before any run? |
|---|---|---|---|
| 1. [Definitions](/rival-ai-incident-definitions/definitions/) | What does each source say counts? | Each definition quoted clause by clause and compared on the same rows | Yes |
| 2. [Rules](/rival-ai-incident-definitions/framework/rules/) | Which coded fields decide each clause? | A yes, no or can't-tell test for each clause, and a list of clauses no field can compute | Yes |
| 3. [Readings](/rival-ai-incident-definitions/readings/) | Where can a clause be read more than one way, and what supports each reading? | Every defensible reading, labeled S, J or B, with one headline reading per clause | Yes |
| 4. [Three-state labels](/rival-ai-incident-definitions/framework/three-state/) | For each incident: yes, no, or can't tell? | A label for every incident, and the range each result can take as the unknowns resolve | Computed |
| 5. [Crosswalk](/rival-ai-incident-definitions/crosswalk/) | On the same incidents, where do the rules disagree? | Which incidents both rules count, which only one counts, and which cannot be told | Computed |
| 6. [Verdicts](/rival-ai-incident-definitions/framework/verdicts/) | Does each result hold at the headline reading, across every reading, and however the unknowns resolve? | One verdict per hypothesis, with the clauses whose reading alone flips it | Criteria yes, verdicts computed |

## Theoretical Foundations

Fields that have reported incidents for decades record harm, near miss, cause and certainty as separate entries where AI-incident definitions use one label, and each has a page under [Theoretical Foundations](/rival-ai-incident-definitions/foundations/).

| Field | What it separates |
|---|---|
| [Aviation](/rival-ai-incident-definitions/foundations/aviation/) | Accidents, serious incidents and incidents |
| [Medical devices](/rival-ai-incident-definitions/foundations/medical-devices/) | Harm that occurred and malfunctions that could cause harm |
| [Pharmacovigilance](/rival-ai-incident-definitions/foundations/pharmacovigilance/) | An adverse event and the strength of evidence that the product caused it |
| [Patient safety](/rival-ai-incident-definitions/foundations/patient-safety/) | Harm that reached a patient, harm that did not, and near misses |
| [Nuclear safety](/rival-ai-incident-definitions/foundations/nuclear-safety/) | Consequences and degraded safety barriers |
| [Cybersecurity](/rival-ai-incident-definitions/foundations/cybersecurity/) | A weakness, its exploitation, and a compromise |
| [Process safety](/rival-ai-incident-definitions/foundations/process-safety/) | Losses and failed or challenged barriers |
| [Public-health case definitions](/rival-ai-incident-definitions/foundations/public-health/) | Confirmed, probable and suspected cases |
